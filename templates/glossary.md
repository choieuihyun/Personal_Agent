# 쉬운 말 대응표

`/setup` 이 사용자와 대화할 때 쓰는 말투 기준이다. 세팅 설명서(`core/setup/*.md`)도 이 기준으로 쓴다.

하네스 안에서 쓰는 말은 만든 사람에게만 익숙하다. 사용자에게는 쉬운 말을 먼저 쓰고,
설정 키나 파일 이름이 꼭 필요하면 뒤에 괄호로 붙인다.

## 말투 규칙

1. **해요체로 말한다.** "~합니다" 보다 "~해요" 가 편하다. 반말은 쓰지 않는다
2. **한 문장에는 한 가지만 말한다.** 문장이 쉼표로 세 번 넘게 이어지면 나눈다
3. **누가, 무엇을, 어떻게 하는지 빼먹지 않는다.**
   - 나쁨: "범위를 제안하고 위험도를 표시한다"
   - 좋음: "explorer 는 고칠 파일 목록을 정해서 알려 줘요. 그 파일이 위험한 곳이면 표시도 해요"
4. **질문하기 전에 이 프로젝트의 실제 파일이나 폴더로 예를 하나 든다.** 예가 없으면 비슷한 프로젝트의 예를 든다
5. **답하면 무엇이 달라지는지 한 문장으로 말한다.** "알려 주시면 explorer 가 그 폴더를 고칠 때 먼저 확인을 받아요"
6. **모르면 넘어가도 된다고 말한다.** "모르시면 넘어가도 돼요. 나중에 채울 수 있어요"
7. **영어 약어와 하네스 용어는 아래 표의 쉬운 말로 바꾼다.** 표에 없는 용어도 같은 방식으로 풀어 쓴다

## 대응표

| 하네스 용어 | 쉬운 말 |
|---|---|
| 에이전트, 서브에이전트 | 역할을 나눠 맡은 AI |
| 오케스트레이터 | 전체 순서를 관리하는 AI |
| 파이프라인 | 일하는 순서 |
| allowed_to_modify, 허가 목록 | 고쳐도 되는 파일 목록 |
| allowed_to_create | 새로 만들어도 되는 파일 목록 |
| forbidden_globs | 절대 고치면 안 되는 파일 |
| risk_globs | 건드리면 영향이 큰 파일 |
| 위험 축 | 고칠 때 조심해야 하는 곳의 종류 |
| SYNC | 여러 기기나 사용자가 같은 데이터를 함께 쓰는 곳 |
| EVENT | 한 곳의 변경을 여러 곳에 알리는 곳 (이벤트, 전역 상태, 메시지 큐) |
| THREAD | 뒤에서 따로 도는 작업 (백그라운드, 비동기) |
| DB | 데이터를 저장하는 곳 |
| LIST | 목록을 새로 그리는 곳 |
| Human Gate, 사람 확인 | 사용자에게 확인받는 단계 |
| 런타임 게이트, 게이트 | 실제로 실행해 보는 검사 |
| 시나리오, E2E | 실제로 실행해 보는 테스트 (화면을 누르거나 API 를 불러 보는) |
| 태그 | 테스트에 붙인 기능 묶음 이름 |
| 도메인 | 기능 묶음 (예: 장바구니, 로그인) |
| DOMAIN.md | 기능 묶음 설명 문서 |
| 어댑터 | 이 프로젝트를 빌드하고 테스트하는 명령 모음 |
| 보충 칸 | 이 에이전트에게 따로 남기는 메모 |
| 수용조건 | 다 됐다고 볼 조건 |
| 명세 동결 | 만들 내용을 확정해서 적어 두기 |
| 목표역산 | 목표에서 거꾸로 따져 보기 |
| DoD, 완료 기준 | 완성 기준 |
| dod_checks | 자동으로 확인할 수 있는 완성 기준 |
| 컨벤션 문서 | 코딩 규칙 문서 |
| ui_test_id | 테스트가 화면 요소를 찾을 때 쓰는 이름표 (예: data-testid) |
| has_ui | 사용자가 보는 화면이 있는지 |
| triage 4분류 | 실패 원인 네 가지: 코드 버그, 가끔 실패, 테스트가 틀림, 환경 문제 |
| FLAKY | 가끔 실패 |
| JUnit XML | 테스트 결과 파일 |
| 무의미 diff | 아무것도 안 바꾸거나 같은 곳만 계속 고치는 수정 |
| NO_FLOW | 실행해 볼 테스트가 없음 |
| exit 3 | 설정이 모자라서 멈춤 |
| MCP | 외부 도구 연결 |
| 역수출 | 쓰지 않는다. "하네스 원본에도 반영" 이라고 말한다 |
