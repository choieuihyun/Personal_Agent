# spec: 만들기 전에 다 됐다고 볼 조건을 확정해서 적어 두는 AI

## 무엇을 하나

spec 은 discuss 가 정한 범위를 다 됐다고 볼 조건으로 바꿔요.
조건은 "이런 상태에서 이렇게 하면 이렇게 보여야 해요" 모양으로 적어요.
이 조건은 반드시 만들기 전에 적어요. 만든 뒤에 결과를 보고 테스트를 쓰면, 만든 그대로 통과하는 빈 테스트가 되기 때문이에요.
조건마다 어디서 시작하는지, 무엇을 누르는지, 무엇을 확인하는지 이름으로 적어요. 그래야 실제로 실행해 보는 테스트로 옮길 수 있어요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 1단계에서 만들 내용을 확정해서 적어 둘 때 불려요. 조건이 비었거나 못 정한 질문이 남으면 다시 불려요. 세 번을 넘기면 사용자에게 확인받아요 |
| `/feature` | 7.5단계에서 실제로 실행해 보는 테스트를 만들 때, 시작 단계가 비어 있으면 다시 불려요 |

## 못 하는 것

- spec 은 이미 있는 파일을 고칠 수 없어요. 고치는 도구(Edit)가 없어요
- 파일을 쓰는 도구(Write)는 결과 파일(`spec.json`)을 저장할 때만 써요. 이건 도구가 아니라 설명서의 규칙으로 막은 거예요
- 사용자에게 직접 묻지 못해요. 묻는 도구(AskUserQuestion)가 없어요. 모르는 것은 못 정한 질문으로 남기고, 전체 순서를 관리하는 AI 가 대신 물어요
- discuss 에서 정하지 않은 범위를 더하지 않아요. 어떻게 만들지도 정하지 않아요. 그건 planner 가 해요

## 넘겨주는 것

spec 은 결과를 `spec.json` 에 적어요. 다 됐다고 볼 조건의 목록이 들어가요.
조건마다 자동으로 실행해서 확인할 수 있는지, 사람이 봐야 하는지를 적어요.
시작 단계, 조작할 대상의 이름, 확인할 대상의 이름, 확인할 글자도 적어요.
planner 는 대상 이름을 테스트가 화면 요소를 찾을 때 쓰는 이름표로 옮겨요.
전체 순서를 관리하는 AI 는 7.5단계에서 이 파일만 보고 실제로 실행해 보는 테스트를 만들어요.
verifier 는 그 이름표가 코드에 실제로 붙었는지 확인해요.

## 여기에 넣으면 좋아지는 것

- 자동 테스트가 로그인을 어떻게 통과하는지 알려 주시면, 사람이 직접 확인해야 하는 조건이 줄어요.
  모바일 앱이면 테스트 빌드에만 있는 로그인 입구, 웹이면 저장해 둔 로그인 상태 파일, 서버라면 테스트용 토큰을 받는 경로 같은 것이에요
- 테스트가 어디서 시작하는지 알려 주세요. 환경마다 달라지는 값을 어떤 이름으로 비워 두는지도 알려 주세요. 그러면 spec 이 시작 단계를 한 번에 정해요
- 테스트 데이터를 만드는 방법을 알려 주시면 준비 단계가 구체적이 돼요. 초기 데이터를 넣는 스크립트, 미리 만든 테스트 데이터 파일(픽스처), 테스트용 API 같은 것이에요
- 여러 기기나 여러 로그인을 동시에 띄워서 테스트할 수 있는지 알려 주세요. 그러면 spec 이 여러 기기 동기화 조건을 자동으로 확인할지 사람이 확인할지 정확히 나눠요
