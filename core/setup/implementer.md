# implementer: 정해진 파일 안에서만 코드를 고치는 AI

## 무엇을 하나

implementer 는 실제로 코드를 고치는 AI 예요.
고칠 파일은 explorer 가 먼저 정하고, 전체 순서를 관리하는 AI 가 허락해요.
implementer 는 그렇게 정해진 파일 목록 안에서만 고쳐요.
버그 고치기와 새 기능 만들기를 둘 다 맡아요.
목록 밖의 파일을 고쳐야 하면 고치지 않고 실패했다고 알려요.
코딩 규칙 문서가 있으면 먼저 읽고 그 규칙대로 써요.
문서가 없으면 주변 코드를 따라 써요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/fix` | 고칠 파일이 정해진 다음, 코드를 고칠 때 불려요. 빌드가 실패하면 다시 불려요. 실제로 실행해 보는 테스트가 실패하고 triage 가 코드 버그라고 판정해도 다시 불려요. 정해진 시도 횟수에 닿으면 멈춰요 |
| `/feature` | 새 기능을 연결할 파일이 정해진 다음, 코드를 만들 때 불려요. 만든 코드를 검사하는 AI(verifier)의 검사나 빌드가 실패하면 다시 불려요. 여러 기기가 같은 데이터를 함께 쓰는 흐름(sync)을 새로 만드는 것은 새 기능 모드(feature-mode) 지시로 허용돼요 |


## 못 하는 것

- 명령을 실행할 수 없어요 (Bash 도구가 없어요). 빌드, 테스트, git 을 돌리지 못해요. 빌드는 builder 가 따로 해요. 그래야 "고쳤다" 는 말을 따로 확인할 수 있어요
- 코드를 검색할 수 없어요 (Grep, Glob 도구가 없어요). 어디를 고칠지는 explorer 가 이미 정했어요. implementer 가 스스로 범위를 넓히지 못하게 하려는 거예요
- 고쳐도 되는 파일 목록 밖의 파일과 빌드 설정 파일은 고치지 않아요 (규칙). 범위를 넘는 수정은 아무도 검증하지 않은 수정이에요
- 코드 전체를 새로 정리하거나(리팩토링), 프로젝트에 없는 구조 패턴을 들여오지 않아요. 다른 언어로 바꾸거나, 다른 코드가 부르는 약속(API)을 바꾸지도 않아요 (규칙). 꼭 필요한 만큼만 고친다는 원칙이에요

## 넘겨주는 것

implementer 는 고친 코드를 파일에 바로 반영해요.
그리고 최근 수정 기록을 남겨요. 바꾼 줄 수, 고친 파일, 수정 내용을 짧게 요약한 값(해시)이 들어가요.
전체 순서를 관리하는 AI 는 이 기록을 보고 수정이 헛돌고 있는지 확인해요.
아무것도 안 바꿨거나 같은 곳만 계속 고치고 있으면 멈춰요.
바뀐 코드는 builder 가 빌드해서 컴파일되는지 봐요.
`/feature` 에서는 verifier 가 완성 기준을 검사해요.

## 여기에 넣으면 좋아지는 것

- 코딩 규칙 문서를 알려 주세요. 그러면 implementer 가 조심해야 하는 곳마다 이 프로젝트의 구체 규칙을 따라요. 예를 들어 모바일 앱은 화면이 닫히면 진행 중인 작업을 취소해요. 웹은 전역 상태(store)를 정해진 방식으로 바꿔요. 서버는 요청을 처리하는 스레드에서 오래 막히는 호출을 하지 않아요
- 테스트가 화면 요소를 찾을 때 쓰는 이름표(예: data-testid)를 알려 주세요. 그러면 implementer 가 고치는 화면의 버튼, 입력 칸, 목록에 이름표를 붙여요. 그래야 실제로 실행해 보는 테스트가 그 요소를 찾을 수 있어요
- 쓰고 있는 구조 패턴을 문서에 적어 두면 "없는 패턴을 들여오지 않기" 규칙이 정확해져요
- 먼저 따라 할 참고 파일이나 손대지 말아야 할 관례를 알려 주면, implementer 가 주변 코드를 보고 짐작하는 일이 줄어요

## 질문

| # | 사용자에게 할 질문 | 스캔으로 추측 | 저장 위치 | 안 채우면 |
|---|---|---|---|---|
| 1 | 코딩 규칙 문서가 있나요? 있으면 경로를 알려 주세요. 구조 패턴, 주석과 이름 규칙, 조심해야 하는 곳별 규칙, 완성 기준을 적어 두는 문서예요. 예를 들어 docs/CONVENTIONS.md 같은 파일이에요 | CONTRIBUTING 문서, docs 폴더의 스타일 문서, 린트 설정 | `docs.conventions` | 코딩 규칙 확인을 건너뛰어요. implementer 는 조심해야 하는 곳마다 정해 둔 기본 규칙과 주변 코드만 따라요 |
| 2 | 테스트가 화면 요소를 찾을 때 쓰는 이름표가 있나요? 예를 들어 웹에서는 data-testid 를 많이 써요. 화면이 없는 프로젝트면 해당 없어요 (화면이 있는지는 planner 를 소개할 때 여쭤봐요) | 기존 코드에서 testTag, testID, data-testid 가 얼마나 쓰이는지 | `ui_test_id` | implementer 가 이름표를 붙이지 않아요. 이름표 규칙 확인도 건너뛰어서, 실제로 실행해 보는 테스트가 화면 요소를 못 찾을 수 있어요 |
| 3 | 고칠 때 먼저 참고하면 좋은 파일이 있나요? 규칙은 아니지만 그동안 피해 온 관례도 알려 주세요. 예를 들어 '새 화면은 로그인 화면 코드를 본떠 만든다' 같은 것이에요 | 알 수 없음 | `.claude/project/agents/implementer.md` | implementer 가 주변 코드만 보고 판단해요 |
| 4 | 기능 묶음마다 절대 깨면 안 되는 규칙이나 자주 빠지는 함정이 있나요? 예를 들어 '결제가 끝나기 전에는 장바구니를 비우지 않는다' 같은 규칙이에요 | 알 수 없음 | `DOMAIN.md` | implementer 가 그 규칙을 모른 채 고쳐요. 기능 묶음 설명 문서를 둔 폴더(docs.domain_map)가 설정되지 않으면 문서를 읽지 않아요 |
