# verifier: 설계도대로 지어졌는지 둘러보고 적기만 하는 준공 검사관

## 무엇을 하나

바뀐 코드가 "다 됐다" 고 할 수 있는 상태인지 검사한다.
기존 코드를 새 방식으로 옮긴 작업이면 빠진 기능, 옛 이름이 남은 곳, 옛 코드에서 새 코드를 못 부르는 곳을 찾는다.
새 기능이면 이 프로젝트가 정한 완료 기준을 지켰는지만 본다. 문제를 찾아 적을 뿐 고치지 않는다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 7단계 검증 + 빌드. 신규 기능 모드로 builder 와 나란히 |
| `/modernize` | 3단계 검증 + 빌드. builder 와 나란히 |
| `/fix` | 불리지 않는다. 빌드와 런타임 게이트만 본다 |

## 못 하는 것

- 파일을 고치거나 쓰지 못한다 (Edit, Write 없음). 검사관이 고치기 시작하면 무엇을 검사했는지 흐려진다
- 결과도 파일로 쓰지 않고 반환만 한다. 오케스트레이터가 `verifier.json` 으로 저장한다
- Bash 는 완료 기준 검사 스크립트와 진척표 확인에만 쓴다. 빌드와 git 은 문서 규칙으로 막혀 있다

## 넘겨주는 것

`verifier.json`: 통과 여부와 문제 목록(종류, 심각도, 파일, 줄).
오케스트레이터가 builder 결과와 합쳐 판단한다. 심각도 MEDIUM 이상이 하나라도 있으면 실패이고,
문제 목록이 implementer 에게 그대로 넘어가 수정 근거가 된다. LOW 는 보고에만 남는다.

## 여기에 넣으면 좋아지는 것

- 기계로 확정되는 완료 기준. 모바일이면 "화면 파일에 미리보기 선언 필수", 웹이면 "컴포넌트에 색상 값 직접 쓰기 금지",
  서버면 "핸들러 파일에 입력 검증 호출 필수" 같은 규칙을 적어 두면 눈대중 대신 매번 같은 결과가 나온다
- 진척표가 있으면 마이그레이션이 끝날 때마다 표가 갱신됐는지 상기시킨다
- 옛 이름이 숨어 있기 쉬운 등록 파일 (앱 매니페스트, 웹 라우트 설정, 서버 의존성 주입 설정) 을 알려 주면 잔존 참조를 덜 놓친다
- 검색에서 뺄 생성 코드나 산출물 폴더를 알려 주면 엉뚱한 잔존 참조 보고가 줄어든다
