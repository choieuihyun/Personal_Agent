# builder: 고친 코드가 빌드되는지 확인하는 AI

## 무엇을 하나

builder 는 프로젝트의 빌드 명령을 돌려서 코드가 컴파일되는지 확인해요.
성공인지 실패인지는 명령이 끝날 때 돌려주는 값(종료코드)으로만 정해요.
실패하면 에러 기록에서 어느 파일 몇 번째 줄인지 뽑아요.
그 위치를 얼마나 믿을 수 있는지도 HIGH, MEDIUM, LOW 로 매겨요.
에러가 있어도 builder 가 직접 고치지는 않아요.
명령을 짐작해서 돌리지도 않아요. 설정에 적힌 명령만 써요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/fix` | 빌드 에러를 고치러 시작했을 때(`--build`), 맨 처음에 불려요. 고칠 에러를 먼저 알아내요. 빌드가 성공하면 고칠 것이 없으니 거기서 끝나요 |
| `/fix` | 코드를 고칠 때마다 불려서 빌드해 봐요 |
| `/feature` | 새 기능 코드를 만든 뒤 불려요. 만든 코드를 검사하는 AI(verifier)와 동시에 돌아요 |

## 못 하는 것

- 파일을 고칠 수 없어요 (Edit, Write 도구가 없어요). 확인하는 AI 가 고치기까지 하면 "빌드가 됐다" 가 무엇을 증명하는지 흐려져요
- 결과를 파일로 저장하지도 못해요. 같은 이유로 쓰기 도구가 없어요. 전체 순서를 관리하는 AI 가 결과를 받아서 저장해요
- 코드를 검색할 수 없어요 (Grep, Glob 도구가 없어요). 에러 위치는 스크립트가 뽑아요
- 빌드 명령 말고 다른 명령, git, 배포와 실행은 하지 않아요 (규칙). builder 는 컴파일만 해요. 앱을 올리고 테스트를 돌리는 일은 실제로 실행해 보는 검사가 맡아요

## 넘겨주는 것

builder 는 빌드 결과를 정해진 모양의 기록(json) 하나로 넘겨요. 안에는 이런 것이 들어 있어요.

- 성공했는지
- 에러를 짧게 요약한 값(에러 해시)
- 에러가 난 파일, 그 위치를 얼마나 믿을 수 있는지
- 한 줄 요약
- 에러 기록 중 중요한 줄 (최대 10줄)

전체 순서를 관리하는 AI 는 같은 에러 해시가 3번 나오면 멈춰요.
위치를 믿을 수 있는 정도를 보고 다음에 할 일을 골라요.

- LOW 이거나, HIGH 인데 에러 파일이 고쳐도 되는 파일 목록 밖에 있으면 explorer 를 다시 불러요. LOW 가 두 번 연속이면 사용자에게 확인받아요
- MEDIUM 이거나, HIGH 이면서 에러 파일이 목록 안에 있으면 implementer 에게 에러를 넘겨요

## 여기에 넣으면 좋아지는 것

- 빌드 명령을 정확히 알려 주면 무엇을 빌드했는지 분명해져요. 예를 들어 모바일 앱은 디버그용 빌드 하나만, 웹은 타입 검사까지 하는 빌드, 서버는 컴파일과 린트를 돌려요
- 컴퓨터마다 다른 도구 경로를 후보로 여러 개 알려 주세요. 개발 도구 모음(SDK)이나 런타임 버전 관리 도구 같은 것이에요. 그러면 다른 컴퓨터에서도 builder 가 도구를 찾아요
- 흔하지 않은 모양의 에러를 알려 주면, 위치를 믿을 수 있는 정도가 LOW 에서 HIGH 로 올라가요. 템플릿 파일이나 리소스 처리 단계에서 나는 에러가 그런 예예요
- 빌드가 오래 걸리거나 캐시를 먼저 지워야 하는 사정을 알려 주면, builder 가 결과를 알릴 때 그 사정을 같이 적어요

## 질문

| # | 사용자에게 할 질문 | 스캔으로 추측 | 저장 위치 | 안 채우면 |
|---|---|---|---|---|
| 1 | 이 프로젝트는 어떤 언어와 도구로 만들어요? 미리 준비해 둔 빌드와 테스트 명령 모음 중에 맞는 것이 있는지 볼게요. 예를 들어 package.json 이 있으면 웹(node) 명령 모음이 맞을 수 있어요 | 빌드 파일 종류 (package.json, 빌드 스크립트, pyproject) | `adapter` | 직접 적은 명령 모음(adapter_inline)도 없으면 설정을 읽지 못해요. 그러면 builder 는 빌드를 시도하지 않고 실패로 알려요 |
| 2 | 맞는 명령 모음이 없으면 빌드 명령을 직접 알려 주세요. 흔한 모양(파일 이름:줄 번호) 말고 다른 모양으로 빌드 에러가 나오면 그것도 알려 주세요. 명령 모음은 맞고 에러 모양만 다르면 에러 모양만 더해요. 맞는 명령 모음이 없으면 명령까지 전부 적어요. 예를 들어 빌드를 npm run build 로 한다면 그대로 알려 주시면 돼요 | package.json 의 scripts, 실패한 빌드 기록 한 번 | `adapter_override` 또는 `adapter_inline` | 고른 명령 모음(adapter)을 그대로 써요. 에러 모양을 안 알려 주면 기본 세 가지 모양만 읽어서, 모양이 다를 때마다 위치 신뢰도가 LOW 가 되고 "빌드 에러 형식 미등록" 이 붙어요. 그러면 `/fix` 는 explorer 를 다시 부르다가 두 번 연속이면 사용자에게 확인받아요 |
| 3 | 빌드 명령에 비어 있는 칸이 있으면 무엇을 넣을까요? 예를 들어 여러 모듈 중 어느 것을 빌드할지 같은 빌드 대상 이름이에요 | package.json 의 scripts, 빌드 스크립트의 작업(task) 목록 | `vars` | 빈칸이 남았다고 알리고 빌드를 시도하지 않아요 |
| 4 | 빌드하기 전에 켜 둬야 하는 환경변수가 있나요? 예를 들어 NODE_ENV=production 같은 값이에요 | 자동 빌드 설정 파일(CI)의 env 항목 | `env` | 환경변수를 설정하지 않고 빌드해요. 그러면 도구를 못 찾거나 버전이 맞지 않아 실패할 수 있어요 |
| 5 | 컴퓨터마다 경로가 다른 환경변수가 있나요? 있으면 후보 경로를 여러 개 알려 주세요. 예를 들어 개발 도구 모음(SDK)이 컴퓨터마다 다른 폴더에 설치된 경우예요 | 흔히 설치되는 경로에 실제로 있는지 | `env_candidates` | 그 환경변수를 빼고 빌드해요. 다른 컴퓨터에서는 도구를 못 찾을 수 있어요 |
| 6 | 빌드에 대해 따로 알아 둘 사정이 있나요? 예를 들어 빌드가 오래 걸린다거나, 무시해도 되는 경고가 있다거나 하는 것이에요 | 알 수 없음 | `.claude/project/agents/builder.md` | builder 는 명령이 끝날 때 돌려주는 값(종료코드)만 보고 판단해요 |
