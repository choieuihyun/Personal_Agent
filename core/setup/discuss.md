# discuss: 만들기 전에 사용자와 이야기해서 만들 범위를 정하는 AI

## 무엇을 하나

discuss 는 새 기능을 만들기 전에 사용자와 대화해서 만들 범위를 정해요.
헷갈리는 것만 묻지 않아요. 예외 상황, 거기서 이어지는 드문 경우, 같이 있으면 좋을 기능을 먼저 꺼내요.
질문과 답은 최대 다섯 차례까지 주고받아요.
끝나면 정한 것, 뺀 것, 못 정한 것을 나눠서 적어요. 어떻게 만들지는 정하지 않아요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 첫 단계(0단계)에서 만들 범위를 이야기할 때 불려요. 결과가 없거나 정한 범위가 비어 있으면 다시 불려요 |
| `/feature` | 4단계에서 사용자가 계획을 보고 고쳐 달라고 해서, 범위 이야기로 돌아올 때 불려요 |

## 못 하는 것

- discuss 는 이미 있는 파일을 고칠 수 없어요. 고치는 도구(Edit)가 없어요. 범위를 정하는 동안 코드가 바뀌면 뒤 단계의 기준이 흔들려요
- 파일을 쓰는 도구(Write)는 있어요. 하지만 결과 파일(`discuss.json`)을 저장할 때만 써요. 이건 도구로 막은 게 아니라 설명서의 규칙으로 막은 거예요
- 어떻게 만들지는 설계하지 않아요. 그건 planner 가 해요. discuss 는 무엇을, 왜, 어디까지 만들지만 정해요
- 저장소 전체를 훑어보지 않아요. 질문할 근거가 되는 코드만 조금 봐요

## 넘겨주는 것

discuss 는 결과를 `discuss.json` 에 적어요. 정한 범위, 뺀 범위, 예외 상황의 처리 방법, 못 정한 것이 들어가요.
조심할 곳 표시도 들어가요. 여러 기기가 같은 데이터를 함께 쓰는지, 외부 시스템이 관여하는지, 변경을 여러 곳에 알려야 하는지 표시해요.
뒤에서 따로 도는 작업이 있는지, 데이터를 저장하는지, 새 입구(화면, API, 명령)가 생기는지, 권한이 필요한지도 표시해요.
전체 순서를 관리하는 AI 는 이 표시를 보고 위험 수준을 올려요.
spec 은 정한 범위를 다 됐다고 볼 조건으로 바꿔요.
planner 는 외부 시스템과 여러 기기 동기화 표시를 설계에 반영해요.

## 여기에 넣으면 좋아지는 것

- 외부 시스템 이름을 알려 주시면 discuss 가 "어느 서버가 관여하나요?" 대신 그 이름을 들어 물어요.
  모바일 앱이면 푸시 서버, 웹이면 결제 대행 API, 서버라면 다른 팀의 메시지 큐 같은 것이에요
- 데이터의 원본이 서버에 있는지 기기에 있는지 알려 주세요. 여러 기기에 동시에 떠 있는지도 알려 주세요. 그러면 discuss 가 둘이 부딪힐 때 어느 쪽을 따를지부터 물어요
- 이 프로젝트에 해당하지 않는 것(오프라인 모드 없음, 권한 구분 없음)을 알려 주시면 필요 없는 질문이 줄어요
- 자주 거절하는 제안을 알려 주시면 discuss 가 범위를 부풀리는 제안을 덜 해요
