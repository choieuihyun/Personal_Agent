# explorer: 고칠 파일을 찾아 주는 AI

## 무엇을 하나

explorer 는 버그 설명이나 에러, 기능 계획을 받아요.
관련 코드를 찾아 읽고 "이 파일들을 고치면 돼요" 하고 고칠 범위를 알려 줘요.
고칠 곳이 조심해야 하는 곳이면 그것도 표시해요.
조심해야 하는 곳은 다섯 종류예요.

- 여러 기기나 사용자가 같은 데이터를 함께 쓰는 곳
- 한 곳의 변경을 여러 곳에 알리는 곳
- 뒤에서 따로 도는 작업
- 데이터를 저장하는 곳
- 목록을 새로 그리는 곳

explorer 는 직접 고치지 않아요.
explorer 가 알려 준 목록으로, 코드를 고치는 AI(implementer)가 손대도 되는 파일이 정해져요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/fix` | 처음에, 어떤 파일을 고칠지 정할 때 불려요. 빌드 에러가 어느 파일에서 났는지 모르거나(위치 신뢰도 LOW), 고쳐도 되는 파일 목록 밖에서 나면 다시 불려요 |
| `/feature` | 계획을 승인받은 뒤, 그 계획을 연결할 기존 파일을 정할 때 불려요. 새로 만들 파일은 설계하는 AI(planner)가 정해요 |

## 못 하는 것

- explorer 는 파일을 고칠 수 없어요 (Edit, Write 도구가 없어요). 찾는 AI 가 직접 고치면 고칠 범위를 스스로 넓힐 수 있어요. 그래서 알려 주는 일과 고치는 일을 도구로 나눠 두었어요
- 결과를 파일로 저장하지도 못해요. 같은 이유로 쓰기 도구가 없어요. 전체 순서를 관리하는 AI 가 결과를 받아서 저장해요
- git 명령을 쓰거나 저장소 전체를 훑지 않아요. 명령 실행 도구(Bash)는 있지만 규칙으로 막아 두었어요. 필요한 곳만 읽어야 AI 가 들고 있는 내용이 불어나지 않아요
- 빌드 설정 파일은 읽지 않아요 (규칙). 의존성을 바꾸는 작업일 때만 예외예요. 대부분의 수정과 상관없고 내용이 많아서예요

## 넘겨주는 것

explorer 는 수정 제안을 정해진 모양의 기록(json) 하나로 넘겨요. 안에는 이런 것이 들어 있어요.

- 고칠 파일, 참고만 할 파일, 무시할 파일
- 조심해야 하는 곳의 종류 (SYNC, EVENT, THREAD, DB, LIST)
- 위험도 (HIGH, MEDIUM, LOW)
- 한 줄 요약

전체 순서를 관리하는 AI 가 이 제안에서 절대 고치면 안 되는 파일을 걸러 내요.
남은 파일이 고쳐도 되는 파일 목록이 돼요.
위험도가 HIGH 면 사용자에게 확인을 받아요.
코드를 고치는 AI(implementer)는 조심해야 하는 곳의 종류를 보고 어떤 수정 규칙을 쓸지 골라요.

## 여기에 넣으면 좋아지는 것

- 조심해야 하는 곳의 종류마다 해당 폴더를 알려 주세요. 그러면 explorer 가 짐작하지 않고 정해진 규칙대로 표시해요. 예를 들어 모바일 앱은 로컬 DB 스키마 폴더를 DB 로, 웹은 전역 상태(store) 폴더를 EVENT 로, 서버는 메시지 큐를 받아 처리하는 폴더를 EVENT 로 정할 수 있어요
- 건드리면 영향이 크게 번지는 공유 파일을 알려 주세요. 그러면 explorer 가 위험도를 최소 MEDIUM 으로 올려서 사람이 한 번 더 봐요. 공통 네트워크 코드, 로그인 확인 미들웨어, 디자인 토큰 파일 같은 것이에요
- 먼저 볼 곳과 피할 곳을 알려 주면 헛걸음이 줄어요. 피할 곳은 자동으로 만들어지는 코드 폴더, 외부 코드를 복사해 둔 폴더, 빌드 결과물 폴더 같은 것이에요
- 이 프로젝트에서 어떤 파일을 빌드 설정 파일로 볼지 알려 주세요. 그러면 읽지 않기 규칙이 정확한 파일에 걸려요
- 기능 묶음 설명 문서가 있으면 explorer 가 용어와 늘 지켜야 할 규칙을 알고 찾아요. 그래서 엉뚱한 파일을 덜 골라요

## 질문

| # | 사용자에게 할 질문 | 스캔으로 추측 | 저장 위치 | 안 채우면 |
|---|---|---|---|---|
| 1 | 고칠 때 조심해야 하는 곳이 다섯 종류 있어요. 종류마다 이 프로젝트의 어느 폴더가 해당하는지 알려 주세요. 여러 기기나 사용자가 같은 데이터를 함께 쓰는 곳(SYNC), 한 곳의 변경을 여러 곳에 알리는 곳(EVENT: 이벤트, 전역 상태, 메시지 큐), 뒤에서 따로 도는 작업(THREAD: 백그라운드, 비동기), 데이터를 저장하는 곳(DB: 저장소, 스키마), 목록을 새로 그리는 곳(LIST: 일부만 갱신하는 목록, 페이지 단위로 불러오는 목록)이에요. 예를 들어 전역 상태를 모아 둔 src/store 폴더는 EVENT 예요. 해당하는 폴더가 없는 종류는 비워 둬도 돼요 | 폴더 이름에 sync, store, queue, worker, migration 이 들어가는지, 상태 관리나 큐 라이브러리를 쓰는지 | `risk_axes` | explorer 가 매번 짐작으로 정해요. 그러다 SYNC 나 EVENT 를 놓치면 위험도가 HIGH 로 안 올라가 사용자 확인 없이 고쳐지고, THREAD 나 DB 를 놓치면 MEDIUM 대신 LOW 로 잡혀요 |
| 2 | 어느 종류라고 딱 정하긴 어렵지만, 건드리면 영향이 크게 번지는 공유 파일이 있나요? 예를 들어 여러 화면이 함께 쓰는 네트워크 코드 같은 파일이에요 | 다른 파일에서 가장 많이 불러다 쓰는(import) 파일 | `risk_globs` | 위험도를 올려 주지 않아서 공유 파일을 고쳐도 LOW 로 지나갈 수 있어요. `/feature` 에서 공유 파일을 고칠 때 사용자에게 확인받는 단계도 걸리지 않아요 |
| 3 | 코드를 찾을 때 먼저 볼 곳이나 피할 곳이 있나요? 빌드 설정 파일로 볼 파일 목록도 알려 주세요. 예를 들어 자동으로 만들어지는 코드가 모인 폴더는 피하면 좋아요 | 자동으로 만들어지는 코드 폴더와 빌드 결과물 폴더, 빌드 스크립트 파일 | `.claude/project/agents/explorer.md` | explorer 가 매번 함수나 클래스 이름 검색부터 시작해요. 어디까지가 빌드 설정 파일인지는 explorer 가 짐작해요 |
| 4 | 기능 묶음마다 용어, 늘 지켜야 할 규칙, 자주 빠지는 함정을 적은 문서가 있나요? 예를 들어 장바구니 기능이라면 '담은 수량은 0보다 작을 수 없다' 같은 규칙이에요 | 알 수 없음 | `DOMAIN.md` | explorer 가 기능에 대한 지식 없이 코드만 보고 판단해요. 기능 묶음 설명 문서를 둔 폴더(docs.domain_map)가 설정되지 않으면 문서 위치를 몰라서 읽지 않아요 |
