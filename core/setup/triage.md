# triage: 실행해 본 테스트가 왜 실패했는지 가려 주는 AI

## 무엇을 하나

triage 는 실제로 실행해 보는 테스트가 실패했을 때 불려요.
그리고 실패 원인을 네 가지 중 하나로 가려요.

- 코드 버그
- 가끔 실패 (타이밍이 늦어서 생긴 실패)
- 테스트가 틀림 (테스트 시나리오 자체의 오류)
- 환경 문제 (실행 환경 때문에 생긴 문제)

triage 는 환경, 테스트, 타이밍을 먼저 의심해요.
셋 다 아닐 때만 코드 버그라고 판정해요.
코드를 괜히 고치는 일을 막기 위해서예요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/fix` | 코드를 고치고 빌드가 된 뒤, 실제로 실행해 보는 검사에서 테스트가 실패했을 때 |
| `/feature` | 새 기능을 만들고 검사와 빌드를 통과한 뒤, 실제로 실행해 보는 검사에서 테스트가 실패했을 때 |

## 못 하는 것

- 파일을 쓸 수 없어요 (Write, Edit 도구가 없어요). 조사하는 AI 가 현장을 고치면 원인이 지워지기 때문이에요
- 코드를 검색할 수 없어요 (Grep, Glob 도구가 없어요). 테스트 실행 결과, 실패한 순간의 화면, 테스트 결과 보고서, 로그만 근거로 삼아요
- 명령 실행 도구(Bash)는 로그를 읽는 데만 써요. 테스트 다시 돌리기, 빌드, 배포는 문서의 규칙으로 막혀 있어요. 다시 돌릴지는 전체 순서를 관리하는 AI 가 정해요

## 넘겨주는 것

triage 는 판정 결과(`triage.json`)를 넘겨요.
안에는 원인 분류, 신뢰도, 근거, 다음에 할 일, 의심 파일이 들어 있어요.
전체 순서를 관리하는 AI 는 이 결과를 보고 다음 길을 골라요.

- 코드 버그면 의심 파일을 들고 implementer 를 다시 불러요
- 가끔 실패면 테스트만 다시 돌려요. 2회를 넘으면 사람이 판단해요
- 테스트가 틀렸으면 테스트를 고쳐요
- 환경 문제면 바로 사용자에게 넘겨요

신뢰도가 LOW 여도 사용자에게 넘겨요.

## 여기에 넣으면 좋아지는 것

- 원래 가끔 실패하는 테스트를 알려 주세요. 그러면 triage 가 그 실패를 코드 버그로 잘못 보고 코드를 계속 고치는 일이 줄어요
- 환경 문제가 어떤 모습으로 나타나는지 알려 주면, triage 가 빨리 사용자에게 넘겨요. 모바일이면 권한 팝업이나 기기 잠금이 그래요. 웹이면 미리보기 서버의 포트 충돌이나 동의 배너가 그래요. 서버면 DB 컨테이너가 안 떠 있거나 스키마가 적용되지 않은 경우예요
- 빌드와 테스트 명령 모음에 로그 명령이 없는 경우(웹, 서버)에는 대신 볼 로그 위치를 알려 주세요. 근거가 하나 늘어서 신뢰도가 올라가요
- 이 프로젝트 로그에서 실패를 뜻하는 표현을 알려 주면, 기본 세 단어에 없는 실패도 잡아요
