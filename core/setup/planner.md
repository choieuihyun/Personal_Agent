# planner: 새 파일을 어디에 어떻게 만들지 계획만 세우는 AI

## 무엇을 하나

planner 는 spec 이 적은 다 됐다고 볼 조건을 보고 만들 계획을 세워요.
어떤 파일을 새로 만들지, 어느 폴더에 둘지, 어떤 기존 코드를 본보기로 삼을지 정해요.
화면이 있으면, 조건에 나온 대상마다 테스트가 찾을 이름표를 어디에 붙일지도 정해요.
만드는 일을 작은 단계로 나누고 조심할 점을 적어요. 코드는 쓰지 않아요.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 2단계에서 만들 계획을 세울 때 불려요 |
| `/feature` | 3단계에서 plan-checker 가 계획을 통과시키지 않으면, 지적받은 내용을 들고 다시 불려요. 세 번을 넘기면 사용자에게 확인받아요 |
| `/feature` | 4단계에서 사용자가 계획을 보고 고쳐 달라고 해서, 계획 세우기로 돌아올 때 불려요 |

## 못 하는 것

- planner 는 이미 있는 파일을 고칠 수 없어요. 고치는 도구(Edit)가 없어요. 파일을 쓰는 도구(Write)는 결과 파일(`plan.json`)을 저장할 때만 써요. 이건 설명서의 규칙으로 막은 거예요
- 라이브러리 추가나 빌드 설정 변경은 계획에 넣지 않아요. 그건 사용자가 따로 허락해야 해요
- 프로젝트에 없던 구조나 새 추상화 층을 들여오지 않아요. 주변 코드가 하는 방식을 따라요
- 고칠 기존 파일은 후보만 적어요. 실제로 고칠 파일을 정하는 건 explorer 가 해요

## 넘겨주는 것

planner 는 결과를 `plan.json` 에 적어요.
새로 만들 파일, 고칠 후보 파일, 본보기 코드, 이름표를 붙일 위치가 들어가요.
주된 기능 묶음, 나눈 단계, 조심할 점도 들어가요.
전체 순서를 관리하는 AI 는 새로 만들 파일을 새로 만들어도 되는 파일 목록에 넣어요.
plan-checker 는 계획이 조건을 다 채우는지 확인해요. explorer 는 고칠 후보 중에서 실제로 고칠 파일을 정해요.
주된 기능 묶음은 테스트에 붙이는 기능 묶음 이름이 돼요. 실제로 실행해 보는 검사는 이 이름을 보고 어떤 테스트를 돌릴지 정해요.

## 여기에 넣으면 좋아지는 것

- 화면이 없는 프로젝트(서버, 라이브러리, 명령줄 도구)라고 알려 주시면, planner 가 이름표 붙이기를 건너뛰고 설계에만 집중해요
- 기능 묶음별 폴더 규칙을 알려 주시면, planner 가 새 파일을 알맞은 폴더에 둬요. 그러면 바뀐 기능 묶음의 테스트만 돌아요.
  모바일 앱이면 기능별 패키지, 웹이면 `src/features/<이름>`, 서버라면 모듈별 폴더 같은 규칙이에요
- 본보기로 삼을 화면이나 API 를 알려 주시면, planner 가 매번 비슷한 곳을 찾느라 헤매지 않아요
- 규칙에 없는 새 폴더를 만들어도 되는지 알려 주세요. 그러면 테스트를 전부 다시 돌리게 되는 배치를 피할 수 있어요

|---|---|---|---|---|
| 1 | 사용자가 보는 화면이 있나요? 예를 들어 앱이나 웹 페이지면 있고, 서버나 라이브러리만 있으면 없어요 | 화면을 만드는 프레임워크를 쓰는지, 화면이나 컴포넌트 폴더가 있는지 | `project.has_ui` | 모르면 화면이 있는 것으로 봐요. planner 가 이름표 붙일 위치를 계속 정하려 해요. 이름표 종류가 정해져 있지 않으면 조심할 점으로 적어요 |
| 2 | 폴더 이름이 곧 기능 묶음인 곳이 있나요? 있으면 세 가지를 알려 주세요. 그 폴더들이 모인 상위 경로, 여러 기능이 같이 쓰는 폴더, 기능 묶음 목록이에요. 예를 들어 src/features/cart 와 src/features/login 이 있으면 상위 경로는 src/features 예요 | 소스 폴더 안에서 기능별로 나뉜 하위 폴더 | `domains.dir_rules` | 무엇을 바꾸든 테스트를 전부 다시 돌려요. 상위 경로가 비어 있는 항목도 규칙으로 치지 않아요 |
| 3 | 한 폴더에 여러 기능의 파일이 섞여 있고, 파일 이름 앞부분으로 기능 묶음이 나뉘는 곳이 있나요? 예를 들어 한 폴더에 cart_list, cart_detail, login_form 이 같이 있는 경우예요 | 같은 폴더에 있는 파일 이름의 공통 앞부분 | `domains.prefix_rules` | 2번과 같아요. 무엇을 바꾸든 테스트를 전부 다시 돌려요 |
| 4 | 새 기능이 지금 있는 기능 묶음 폴더에 맞지 않으면 새 폴더를 만들어도 되나요? 된다면 어디에 두나요? 예를 들어 "src/features 아래에 새로 만들어도 돼요" 처럼 답해 주세요 | 알 수 없어요 | `.claude/project/agents/planner.md` | planner 가 되도록 규칙이 아는 폴더에 새 파일을 둬요. 그럴 수 없으면 주된 기능 묶음 이름을 적어서, 테스트에 붙이는 이름으로만 맞춰요 |
| 5 | 새 화면이나 새 API 를 만들 때 본보기로 삼을 기존 코드가 있나요? 예를 들어 "새 화면은 상품 목록 화면처럼 만들어 주세요" 같은 것이에요 | 최근에 만든 같은 종류의 파일 | `.claude/project/agents/planner.md` | 코딩 규칙 문서가 없으면 planner 가 비슷한 기존 코드 한 곳을 스스로 골라 근거로 삼아요 |
