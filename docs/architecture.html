Personal Agent Harness

하네스 해부도

슬래시 커맨드 하나가 서브에이전트 여러 개를 몰아 탐색부터 실기기 검증까지 돌린다. 그 골격이 어떻게 생겼고, 어디서 멈추며, 왜 다른 프로젝트로 옮길 수 있는지에 대한 해부도.

기준 2026-08-31 실측 출처 안드로이드 프로젝트에서 반입 후 일반화 저장소 choieuihyun/Personal_Agent

01전체 루프

파이프라인은 한 줄이다. 문제를 받아 파일 범위를 정하고, 고치고, 빌드하고, 실기기에서 돌려보고, 깨지면 원인을 분류해 되돌아간다. 이 루프가 스스로 멈출 줄 아는 것이 핵심이다.

LLM 에이전트 단계 — 비결정적, 토큰 소모 결정적 셸 단계 — LLM 미개입, 토큰 0 상태 파일

주목할 것은 게이트만 색이 다르다는 점이다. 다른 단계는 전부 LLM이 판단하지만 런타임 게이트는 셸 스크립트다. 빌드하고 설치하고 테스트를 재생하고 결과를 JSON으로 떨어뜨린다. 판단이 없으니 매번 같은 결과가 나오고, 토큰을 쓰지 않는다. 비결정적인 것을 결정적인 것으로 붙잡는 자리가 여기다.

023층 구조

무엇이 프로젝트를 옮겨도 그대로이고, 무엇이 매번 새로 채워지는가. 이 경계가 이식 가능성의 전부다.

왜 이 경계가 중요한가 가운데 층은 오랫동안 “결합”으로 오해받는다. 실제로는 빈칸이다. 도메인 목록 22개는 특정 제품 지식이지만, 그걸 읽는 알고리즘(경로 파싱 → 폴더 우선 → 긴 접두사 우선 → 모르면 전체 회귀)은 어느 프로젝트에서나 같다. 빈칸을 코드 밖으로 빼는 순간 위층이 통째로 이식 가능해진다.

03파이프라인 3종

셋은 같은 몸통을 쓴다. 갈리는 곳은 몸통에 들어가기 전과 검증 테스트를 어디서 가져오는가 두 군데뿐이다.

자기충족 함정을 피하는 두 가지 방법

회귀 테스트를 구현 후에 쓰면 구현을 그대로 베끼게 된다. 통과는 하지만 아무것도 검증하지 않는다. 두 파이프라인이 이 함정을 각자 다르게 피한다.

파이프라인테스트 출처회피 축no_flow 의 의미
/feature동결된 수용조건출처축 — 명세에서 쓴다조건부 통과 비-UI 기능일 때만
/fix기존 flow 또는 신규기회주의 — 시나리오로 관찰 가능한 버그일 때만조건부 통과 runtime_observable=false 일 때만
같은 신호, 다른 해석 no_flow는 “재생할 테스트가 없다”는 같은 신호인데 파이프라인마다 뜻이 반대다. 마이그레이션에서는 보존을 증명 못 했으니 실패고, 버그 수정에서는 비-UI 버그라면 정상이다. 신호를 맥락에 따라 다르게 읽도록 문서에 못 박아 두는 것이 이 설계에서 제일 미묘한 부분이다.

04/fix 해부

가장 자주 도는 파이프라인. 원래 세 개의 커맨드였던 것을 하나로 합쳤다 — /bugfix는 45%, /crashfix는 61%가 /fix와 글자 단위로 같은 줄이었다. 다른 것은 문제를 어디서 가져오는가뿐이었다.

합치면서 함께 닫힌 구멍

합치기 전합친 뒤
금지 글롭이 3개 파일에 복제 — 한 곳 고치면 나머지 둘이 드리프트1곳
무의미 diff 검사가 4종 / 3종 / 4종으로 갈림4종으로 통일
/crashfix에 런타임 게이트가 없음 — 크래시를 고치는데 앱을 안 켜봄공통 3.5단계를 물려받음
/bugfix의 앵커 없는 “fix 와 동일하다” 참조 4곳소멸
경계 규칙 /feature는 /fix에 합치지 않는다. 인테이크가 다른 건 합치고, 제어 흐름이 다른 건 나눈다. 버그의 세 인테이크(manual, build, crash)는 앞단만 갈리지만 신규 기능은 순서 자체가 다르다 — 승인에서 멈추고, 시나리오를 구현이 아니라 명세에서 만든다. (마이그레이션 전용이던 /modernize는 2026-09-30 에 없앴다. 범용 파이프라인이 아니다)

05에이전트 11개

각 에이전트는 독립 컨텍스트에서 돌고 오케스트레이터에는 결론 JSON만 반환한다. 파이프라인이 길어져도 컨텍스트가 부풀지 않는 이유이자, 권한을 물리적으로 가를 수 있는 이유다.

핵심 설계 “고치지 마”라고 프롬프트에 부탁하지 않는다. 프론트매터의 tools:에서 Edit/Write를 빼버린다. 탐색 에이전트는 파일을 고칠 능력 자체가 없다. 지시를 어길 수가 없다.

코드를 실제로 바꿀 수 있는 것은 11개 중 1개(implementer)다. 그 하나조차 orchestrator.json의 allowed_to_modify 목록 밖은 건드리지 않는다. 목록은 explorer가 제안하고 오케스트레이터가 금지 글롭으로 걸러 확정한다 — 제안하는 쪽과 승인하는 쪽이 분리돼 있다.

06상태기계

orchestrator.json 하나가 유일한 권위다. 에이전트는 각자 JSON을 반환하지만 상태를 쓰는 것은 오케스트레이터뿐이다. 필드는 세 부류로 나뉜다.

세션 격리

호출마다 SESSION_ID를 만들고 그 아래에만 상태를 쓴다. 같은 저장소에서 파이프라인을 동시에 두 개 돌려도 서로의 상태를 덮지 않는다. 

SESSION_ID="fix-$(date +%Y%m%d-%H%M%S)-$(openssl rand -hex 2)"
SESSION_DIR=".claude/state/sessions/${SESSION_ID}"

${SESSION_DIR}/
  orchestrator.json   ← 유일한 권위
  intake.json         ← 문제 출처 (모드 무관 공통 스키마)
  implementer.json    ← 패치 이력 (링 버퍼)
  builder.json        ← 빌드 결과
  runner.json         ← 게이트 결과 (셸이 기록)
  triage.json         ← 실패 분류

07런타임 게이트

이 파이프라인에서 유일하게 LLM이 개입하지 않는 구간. 빌드가 통과했다는 것과 화면이 실제로 동작한다는 것은 다른 얘기이기 때문에 있다.

측정이 셸로 내려간 이유 기록을 문서 단계에 맡겼을 때 게이트를 27회 돌리고 메트릭이 1줄만 쌓여 있었다. 결정적으로 도는 자리로 옮긴 뒤에야 실제로 누적되기 시작했다. 자동화의 측정층은 자동화 자체보다 먼저 무너진다.

선택적 재생

테스트가 쌓이면 전체 재생은 시간이 선형으로 폭발한다. 그래서 바뀐 파일의 도메인 태그를 산출해 그 도메인 테스트만 돌린다. 공유 코드를 건드렸으면 전체 회귀로 떨어진다. 

TAGS=$(python3 domains_for.py <바뀐 파일들>)
bash runtime_gate.sh "${SESSION_DIR}" "" "$TAGS"

# TAGS=message      → message 태그 테스트만 재생
# TAGS=profile      → 그 도메인 테스트 0개 → NO_FLOW (정직한 신호)
# TAGS=ALL          → 전체 재생 ... 이지만 다음 절 참조

08멈추는 법

자동 루프에서 제일 중요한 것은 시작이 아니라 종료다. LLM은 “고쳤습니다”라고 말하면서 아무것도 안 바꿀 수 있고, 같은 자리를 무한히 맴돌 수 있다.

무의미 diff 검사 4종

수정 직후 implementer.json의 패치 이력을 본다. 넷 중 하나에 걸리면 루프를 끊는다.

09도메인 매핑

바뀐 파일에서 도메인을 못 뽑으면 전체 회귀로 떨어진다. 안전한 폴백처럼 보이지만, 테스트가 전 도메인을 덮을 때만 참인 이야기다.

왜 폴더가 접두사보다 나은가

배치판정 방식유지보수누락을 잡을 수 있나
<루트>/<도메인>/폴더 이름으로 자동 (dir_rules)없음잡힌다 실제 트리와 대조
<루트>/ (평면)접두사 등록 필요 (prefix_rules)파일마다 손으로못 잡는다 기계가 도메인을 모름

이 비대칭이 결정적이다. 폴더 누락은 자기 점검으로 잡히지만 접두사 누락은 잡을 방법이 없다. 그 파일이 어느 도메인에 속하는지 기계가 알 수 없기 때문이다. 그래서 새 파일은 폴더에 두는 것을 완료 기준에 넣었다. 

$ domains_for.py --self-check
<소스 루트>: known 22개가 실제 폴더와 일치

도메인 표는 이제 코드가 아니라 project.json 의 domains 에 있다. 규칙 종류는 둘뿐이다 — 폴더 이름이 곧 도메인인 경우(dir_rules)와 파일명 접두사가 도메인을 가리키는 경우(prefix_rules). 설정이 없으면 매핑은 전부 ALL 이다. 모르면 넓게 도는 쪽이 안전하기 때문이다.

이 점검이 처음 잡아낸 것 등록된 폴더 22개 중 8개가 빠져 있었다 — 파일 47개가 조용히 전체 회귀로 떨어지고 있었다. 게다가 등록돼 있던 폴더 하나는 소스가 0개였다. 코드가 옮겨간 뒤 목록만 남은 것이다. 손으로 관리하는 목록은 반드시 현실과 어긋난다. 어긋남을 잡는 장치가 목록보다 중요하다.

10이식 구조

다른 프로젝트에 올리는 절차. 로직은 복사하고, 빈칸은 스캔해서 채우고, 지식은 새로 쓴다.

새 프로젝트 셋업

단계명령하는 일사람 개입
1harness init --adapter …project.json 생성, 명령 기본값 채움없음
2harness scan소스 트리에서 도메인 목록 초안 추출없음
3—애매한 항목만 손본다여기만
4harness installcore/ 복사 + 버전·해시 기록없음
5harness doctor명령·도구·도메인 목록 존재 확인없음

3번만 사람이 한다. 도메인 목록은 폴더 구조에서 뽑히고, 사람이 판단할 것은 이름만으로 소속이 안 갈리는 소수 파일뿐이다. 이 단계까지가 하루가 안 걸리는 일이고, 그 뒤 CLAUDE.md와 회귀 테스트를 채우는 것은 원래 프로젝트마다 새로 하는 일이라 이식 대상이 아니다.

3–5단계에서 바뀐 것

core/ 는 이제 무엇을 어떤 순서로 판정하는지만 안다. 어떤 명령으로 하는지는 어댑터가, 그 명령의 빈칸은 project.json 이 답한다.

층답하는 질문바뀌는 주기
core/어떤 순서로 무엇을 판정하는가방법론이 바뀔 때만
adapters/<스택>.json그 일을 어떤 명령으로 하는가스택을 바꿀 때
.claude/project.json그 명령의 빈칸에 무엇을 넣는가프로젝트마다
설정이 없을 때가 설계의 시험대다 무엇이 안전인지는 스크립트마다 다르다. 도메인 매핑은 모르면 넓게 도는 것이 안전하고(ALL), 런타임 게이트는 모르면 멈추는 것이 안전하다(exit 3). 로더가 둘을 통일해 예외를 던지면 게이트가 조용히 SKIP 되어 초록불이 켜진다. 그래서 로더는 성패만 알리고 판단은 부르는 쪽이 한다.

검증은 눈이 아니라 명령으로 한다. 저장소 루트의 check.sh 가 회사 식별자 0건, 하드코딩된 스택 명령 0건, 에이전트 접두사 0개, 설정 없을 때의 종료값 세 가지를 확인한다.

정리 순서

  1. 원본 커밋 — 되돌릴 기준선 확보 — 완료
  2. 제외 대상 정리 — 삭제 5개, tools/ 로 이동 8개 — 완료
  3. project.json 도입 — 도메인 표와 명령을 코드 밖으로 — 완료
  4. adapters/ 분리 — 빌드·재생 명령을 어댑터 파일로 — 완료
  5. 에이전트 개명 13개 — 제품 접두사 제거 — 완료 (3–4단계보다 먼저 실행)
  6. (다음) bin/harness CLI
6번은 아직 이르다 프로젝트가 하나뿐인데 배포 도구부터 만들 이유가 없다. 1–5만 해도 “복사해서 손으로 채우면 도는” 상태가 되고, 두 번째 프로젝트가 실제로 생겼을 때 무엇이 정말 불편한지 알게 된 다음에 CLI를 만드는 편이 낫다.

검증되지 않은 것

/fix --build는 실기기에서 완주했다 — 세션 격리, 인테이크 분기, 빌드 성공 시 조기 종료까지 확인됐고 진행 중이던 코드는 건드리지 않았다. 다만 explorer 이후 경로와 런타임 게이트 전체는 아직 실전에서 안 돌았다. 실제 에러나 실패하는 테스트가 있을 때 확인된다.

일반화 이후로는 더 좁다. 새 게이트는 스텁 어댑터로만 완주를 확인했다 — 배포/재생/커버리지/NO_FLOW/설정 없음 경로가 각각 의도한 종료값을 냈다. 실제 프로젝트에 다시 얹어 완주시킨 적은 없다. 그것이 다음 검증이다.

이 문서는 Personal_Agent/docs/architecture.html 에 있다. 구조가 바뀌면 같은 작업 안에서 여기도 고친다 — 문서가 코드보다 오래 살아남으면 다음 사람이 틀린 그림을 믿는다.
