# Personal Agent Harness

AI 코딩 에이전트를 프로젝트에 붙이는 오케스트레이션 하네스.
특정 프로젝트의 코드가 아니라, 어떤 프로젝트에든 얹을 수 있는 **뼈대**를 담는다.
그 위에 입힐 **살**(도메인 지식, 프로젝트 사정)은 설치한 뒤 AI 와 대화하며 채운다.

```bash
bash install.sh <내 프로젝트>     # 1. 설치
```
```
/setup                            # 2. 내 프로젝트에서 Claude Code 를 열고 세팅 (대화)
/fix 장바구니가 새로고침하면 빈다   # 3. 사용
```

---

## 커맨드

| 커맨드 | 하는 일 |
|---|---|
| `/fix` | 버그 수정. 탐색 → 수정 → 빌드 → 런타임 검증 → 문서화. 인테이크는 버그 설명, 빌드 에러(`--build`), 크래시 리포트(`--crash`) 셋 |
| `/feature` | 신규 기능. 토론 → 명세 동결 → 설계 → 계획 검증 → **사람 승인** → 구현 → 검증 → 명세에서 만든 시나리오로 런타임 검증 |
| `/setup` | 세팅. 에이전트를 하나씩 소개하며 이 프로젝트의 사정을 대화로 채운다 |
| `/study` | 학습. 공식 문서와 이 저장소의 실제 코드를 대조해 개념을 설명한다 |
| `/deep` | 학습. 한 주제를 내부 동작, 메모리, 실행 관점, 실행 가능한 코드 순서로 깊게 판다 |

## 어떻게 도나

`/fix` 한 번은 이렇게 흐른다.

```
/fix
 ├ explorer (LLM)        어디를 고칠지 찾는다              → save_result.py 가 결과를 검사해 저장
 ├ implementer (LLM)     허가된 파일만 고친다
 ├ builder (LLM)         빌드를 돌린다                     → build_errors.py 가 에러 위치와 해시를 뽑는다
 ├ domains_for.py        바뀐 파일로 도메인 태그를 낸다
 ├ runtime_gate.sh (셸)  런타임 게이트
 │   ├ harness_config.py   설정을 읽는다
 │   ├ e2e_tags.py         그 태그의 시나리오가 있는지 본다
 │   ├ 올리기 → 시나리오 재생 → 내리기 (셸이 직접)
 │   ├ parse_runner.py     JUnit 결과를 읽어 runner.json 을 쓴다
 │   └ record_metric.py    메트릭을 쌓는다
 ├ triage (LLM)          실패했으면 원인을 4가지로 분류한다
 └ documenter (LLM)      도메인 문서를 갱신한다
```

### LLM, 파이썬, 셸의 역할

| 누가 | 무엇을 | 왜 여기에 두나 |
|---|---|---|
| **LLM (에이전트)** | 판단이 필요한 곳만. 어디를 고칠지, 어떻게 고칠지, 실패 원인이 무엇인지 | 코드를 읽고 추론해야 하는 일 |
| **셸** | 흐름. 빌드, 서버나 앱 올리기, 테스트 실행, 내리기를 순서대로 돌리고 종료값으로 판정한다 (`runtime_gate.sh`, `install.sh`) | 외부 명령을 돌리고 종료값을 받는 일은 셸이 자연스럽다 |
| **파이썬** | 계산. json 과 JUnit XML 을 읽고, 경로에서 도메인을 뽑고, 에러 위치와 해시를 만들고, 에이전트 반환을 검사한다 | 구조화된 데이터와 정규식은 셸로 다루기 어렵다 |

판정과 기록을 LLM 에 맡기지 않는 이유는 셋이다.

- **입력이 같으면 결과도 같아야 한다.** 에러 해시를 LLM 이 지으면 같은 에러도 값이 흔들려 "같은 에러 3번이면 멈춘다" 가 안 걸린다
- **LLM 이 중간에 멈춰도 기록은 남아야 한다.** 메트릭 기록을 커맨드 문서 마지막 단계에 맡겼을 때는 게이트를 27번 돌리고 기록이 1줄 남았다
- **토큰이 들지 않는다**

## 설계 원칙

- **상태는 `orchestrator.json` 하나가 갖는다.** 단계, 시도 횟수, 수정 허가 목록, 종료 사유가 여기 있다
- **도구 권한은 프롬프트로 부탁하지 않고 설정으로 막는다.** 에이전트 정의의 `tools:` 에 없는 도구는 못 쓴다.
  explorer, builder, verifier, triage 는 쓰기 권한이 없어서 결과를 반환만 하고, 저장은 스크립트가 형식을 검사한 뒤 한다
- **컨텍스트 격리.** 각 에이전트는 독립 컨텍스트에서 돌고 결론 json 만 넘긴다. 파이프라인이 길어져도 컨텍스트가 안 부푼다
- **무한 루프는 상한으로 끊는다.** 시도 5회, 같은 에러 3회, 아무것도 안 바꾸거나 같은 자리를 맴도는 수정(무의미 diff 4종)
- **실패는 4가지로 나눈다.** 실제 버그, 간헐 실패, 시나리오 오류, 환경 문제. 각각 다음 행동이 다르고 상한을 넘으면 사람에게 넘긴다
- **모르는 것을 아는 척하지 않는다.** 설정이 없으면 통과가 아니라 "모름" 으로 멈추거나 넓게 돈다 (아래 표)

## 뼈대와 살

| 층 | 무엇 | 어디 | 누가 정하나 |
|---|---|---|---|
| 뼈대 | 파이프라인 순서, 에이전트 역할, 도구 제한, 반환 형식, 판정 규칙, 위험 축 이름, 결과 형식(JUnit XML) | `core/` | 하네스 (고정) |
| 선택지 | 아키텍처, 공유 상태 경로, 테스트 도구, UI 식별자 속성, 에이전트에 붙일 MCP | `templates/choices.md` | 사용자가 고른다 |
| 살: 값 | 빌드 명령, 도메인 규칙, 수정 금지 파일, 위험 지점, 문서 위치 | `.claude/project.json` | `/setup` 대화 |
| 살: 명령 | 그 스택에서 빌드하고 올리고 재생하는 법 | `adapters/*.json`, `adapter_inline`, `adapter_override` | 준비된 어댑터 또는 `/setup` 이 작성 |
| 살: 도메인 지식 | 용어, 불변식, 위험 지점, 실제로 터졌던 함정 | `<docs.domain_map>/<도메인>/DOMAIN.md` | `/setup` 대화, 이후 documenter 가 갱신 |
| 살: 에이전트 사정 | 그 에이전트가 더 볼 곳, 피할 곳, 우선순위 | `.claude/project/agents/<에이전트>.md` | `/setup` 대화 |

뼈대를 프로젝트마다 새로 쓰지 않는 이유: 에이전트끼리는 반환 필드 이름으로 다음 단계를 고른다.
프로젝트마다 본문을 고치면 그 계약이 조용히 깨지고, 하네스를 고쳐도 설치된 곳에 전달되지 않는다.
도메인 지식을 에이전트 칸이 아니라 DOMAIN.md 에 두는 이유: 여러 에이전트가 같은 지식을 읽는다. 에이전트마다 복사하면 하나만 고쳐지고 나머지가 낡는다.

## 대상 범위

**모든 프로젝트가 대상이다.** 앱, 웹, 서버, 라이브러리, CLI 를 가리지 않는다. 런타임 게이트의 모양은 하나다.

```
빌드 → (있으면) 올리기 → 도메인 태그로 시나리오를 골라 재생 → JUnit 결과로 판정 → (올렸으면) 내리기
```

| 유형 | 올리기 | 시나리오 예 |
|---|---|---|
| 모바일 앱 | 기기에 설치 | 화면 조작 (maestro 등) |
| 웹 앱 | 미리보기 서버 | 브라우저 조작 (playwright 등) |
| 서버 | 서버 기동, 준비 대기 | API 호출 |
| 라이브러리, CLI | 없음 | 통합 테스트, 명령 실행 |

테스트 도구는 무엇이든 된다. 결과를 JUnit XML 로 남길 수만 있으면 되고, 거의 모든 도구가 직접 또는 리포터 하나로 지원한다.
맞는 어댑터가 없으면 `/setup` 이 그 스택의 명령을 `adapter_inline` 으로 직접 쓴다.

### 검증 현황

| 스택 | 어댑터 | 상태 |
|---|---|---|
| 안드로이드 (gradle + maestro) | `android-gradle-maestro` | 사내 프로젝트에서 사용 (지금 문서 이전 버전) |
| 웹 (React + Vite + Playwright) | `node-vite-playwright` | 샘플 앱에서 설치 → `/setup` → `/fix` 완주 |
| 서버 (Node 내장 http + node:test) | 없음. `/setup` 이 `adapter_inline` 작성 | 샘플 API 에서 설치 → `/setup` → `/fix` 완주 (서버 기동과 내리기 포함) |
| 파이썬 (pytest) | `python-pytest` | 스키마만 맞춤 |

`/feature` 는 아직 실제로 돌려 보지 않았다.

## 설치

```bash
bash install.sh <대상 프로젝트>            # 무엇이 일어날지만 보려면 --dry-run
```

`cp -r` 를 대신 쳐 주는 것이 목적이 아니다. `cp` 가 말해 주지 않는 것을 말하는 게 목적이다.

- **설치한 뒤 대상에서 고친 파일이 있으면 멈춘다.** 목록을 보여 주고 `--force` 를 요구한다.
  기준은 설치 기록(`.claude/.harness-manifest`)이다. 하네스가 갱신한 파일은 고친 파일로 치지 않고 그냥 갱신한다.
  대상에서 고친 것은 하네스로 먼저 옮긴다 (역수출). 안 그러면 조용히 사라진다
- **`project.json` 과 `.claude/project/` 는 덮지 않는다.** 세팅 결과가 날아가면 게이트가 통째로 멈춘다
- 하네스에서 없앤 커맨드와 에이전트가 남아 있으면 지운다. 그 밖의 대상 전용 파일은 건드리지 않는다
- `/setup` 이 붙인 MCP 는 재설치 뒤 다시 반영한다
- `.claude/state/` 와 바이트코드 캐시를 `.gitignore` 에 넣는다
- 설치 직후 설정이 읽히는지와 도메인 규칙을 확인해서 보여 준다. 게이트를 실제로 돌리지는 않는다

필요한 것: `bash`, `python3`, Claude Code.

에이전트는 `.claude/agents/<이름>/AGENT.md` 로 설치된다. Claude Code 는 하위 폴더까지 훑고 식별자는 frontmatter 의 `name` 이다.
같은 폴더에서 `name` 이 겹치면 하나가 조용히 버려지므로 에이전트마다 폴더를 따로 둔다.

## 세팅 (`/setup`)

코드를 먼저 훑어 추측을 내놓고, 모르는 것만 묻는다.

1. **게이트가 돌 수 있게:** 프로젝트 유형(화면이 있나), 테스트 도구와 어댑터, 빌드 명령, 시나리오 위치, 도메인 규칙, 수정 금지 파일
2. **도메인 지식:** 도메인마다 용어, 불변식, 위험 지점, 그리고 코드만 봐서는 절대 모르는 **실제로 터졌던 함정**
3. **에이전트 하나씩:** 무엇을 하는 에이전트인지, 무엇을 못 하는지, 누구에게 무엇을 넘기는지 먼저 소개한다.
   그다음 이 프로젝트에서 더 볼 곳과 피할 곳을 묻고, 도움이 되는 에이전트에는 **붙일 MCP 가 있는지** 묻는다 (필수 아님)
4. **확인:** 채운 설정으로 실제로 빌드와 게이트를 돌려 보고, 비운 것과 그 결과를 표로 남긴다

아키텍처나 도구는 강요하지 않는다. 선택지를 보여 주고 사용자가 고른다.
"나중에" 라고 하면 비워 두고, 다시 `/setup` 을 부르면 이어서 한다.

### AI 에게 포팅을 맡길 때

이 저장소 주소를 AI 에게 주고 "내 프로젝트에 붙여 줘" 라고 해도 된다. 그 AI 는 이 절을 따른다.

1. `install.sh <대상 프로젝트>` 로 설치한다. 파일을 손으로 골라 복사하지 않는다
2. 설치 후 대상 프로젝트에서 `/setup` 의 절차(`.claude/commands/setup.md`)를 따라 **사용자와 대화하며** 세팅한다.
   project.json 을 추측으로 한 번에 채우고 끝내지 않는다. 에이전트마다 무엇을 하는지 사용자에게 설명하고 묻는다
3. `.claude/agents`, `.claude/commands`, `.claude/scripts`, `.claude/adapters` 는 고치지 않는다.
   바꾸고 싶어지면 `project.json` (값), `adapter_inline` 이나 `adapter_override` (명령), 보충 칸 (에이전트 사정) 으로 받는다
4. 게이트를 꺼서(`runtime_gate: false`) 초록불을 만들지 않는다. 끄는 것은 사용자가 결정한다
5. 하네스 자체의 결함을 찾으면 대상에서 고치지 말고 사용자에게 보고한다. 하네스 저장소에서 고쳐 재설치한다

이 저장소 루트의 `CLAUDE.md` 는 **하네스 관리자용** 작업 규칙이다. 포팅하는 쪽에는 적용되지 않는다.

### 설정이 비었을 때 무엇이 일어나는가

설정이 비어 있어도 파이프라인은 돈다. 다만 **모르는 것을 아는 척하지 않는다.**

| 상황 | 결과 | 왜 |
|---|---|---|
| `domains` 없음 | 전부 `ALL` (전체 회귀) | 좁혀서 회귀를 놓치는 것보다 느린 게 낫다 |
| 어댑터 없음 | 게이트 `exit 3`, `gate_error: bad_config` | 통과가 아니다. 조용히 SKIP 되면 초록불로 오인된다 |
| `runtime_gate: false` | `skipped`, `exit 0` | 안 쓰기로 한 것은 정상이다. 보고에 SKIP 으로 남는다 |
| 어댑터 명령의 빈칸 | 게이트 `exit 3`, `unfilled_vars` | 반쪽 명령을 실행하지 않는다 |
| `dod_checks` 없음 | `exit 2` (`DOD_NO_RULES`) | 검사하지 않은 것과 통과한 것은 다르다 |
| `project.has_ui` 없음 | 화면이 있는 것으로 본다 | 화면 전용 검사를 조용히 끄지 않는다. 서버나 라이브러리면 `false` 로 둔다 |

채우는 만큼 좁고 빨라지는 구조다. 손으로 확인하려면:

```bash
python3 .claude/scripts/harness_config.py --export             # 설정이 읽히나, 빈칸은 없나
python3 .claude/scripts/domains_for.py --self-check            # 도메인 목록이 실제 폴더와 맞나
python3 .claude/scripts/domains_for.py src/features/cart/A.ts  # 태그가 제대로 나오나
python3 .claude/scripts/e2e_tags.py --coverage <시나리오 폴더>   # 시나리오가 덮는 도메인
```

## 저장소 구조

| 디렉터리 | 내용 | 대상에 설치되나 |
|---|---|---|
| `core/commands/` | 커맨드: fix, feature, setup, study, deep | 예 |
| `core/agents/` | 역할별 서브에이전트 11개 | 예 |
| `core/setup/` | 에이전트별 세팅 설명서. `/setup` 이 에이전트를 소개하고 묻는 데 쓴다 | 예 |
| `core/scripts/` | 결정적 단계: 런타임 게이트(셸), 설정 로더, 도메인 매핑, 결과 파싱과 저장, 빌드 에러 추출, 완료 기준 검사, 메트릭, 설치 기록 (파이썬) | 예 |
| `adapters/` | 스택별 명령 묶음 | 예 |
